# 合并地形 (#215)

每个外部单元格的地形都是一个网格实体，每个单元格共享一个地形
材料。如今，引擎在每个单元格中绘制四个象限实体，每个象限实体都有自己的材质；
对于 17 x 17 环，大约 7 毫秒的渲染线程时间用于该簿记。

转换器写入数据（`shared::terrain_mesh`）；这个文件是引擎端的。

## 输入

|文件 |转换后的输出根|下什么 |
|---|---|---|
|土地纹理表| `terrain/land-textures.json` (`LAND_TEXTURE_TABLE_PATH`) |类数组和 LTEX FormID 到 id 表 |
|纹理数组 |该表的 `arrays[].path`，例如`terrain/land-diffuse-bc1-1024.ktx2` |每类一个 `texture_2d_array`（用途、块格式、大小），全 mips |
|细胞块| `terrain/<wrld:08x>/chunk_<cx>_<cy>.rkyv` (`terrain_chunk_path`) | A `TerrainChunkFile`：4 x 4 单元的单元网格 |

没有表格的转换是 `absent`：每个单元格都采用今天的象限路径，没有
每个单元格的消息。无法验证的表、无法绑定它的设备、无法验证的数组文件
与表不匹配、数组无法加载或验证或设置未完成
在 `SETUP_TIMEOUT`（120 秒）内是 `refused`：一个错误行，包含原因和相同的后备。
合约外的表类（格式或大小`LandTextureTable::validate`未列出）
故意拒绝整个运行过程中的合并地形：转换器对列表外的格式进行转码
进入 BC7 类，因此仍然命名为 1 的表是转换器故障，不满足于工作
一次围绕一个细胞。

## 每个单元格

1. 流代码向 `TerrainMerge::lookup` 请求单元格。一个块文件被打开一次
   （内存映射，由 rkyv 验证）并保存在一个小缓存中；丢失的块或单元格条目是
   `NoData`，根据表失败 `TerrainCellMesh::validate` 的单元格是 `Invalid`。
2. 单元格的接缝重复项必须一致，且法线不得为零；否则为 `Invalid`。
3.单元格的33 x 33高度和普通网格经过相同
   `validate_and_register_terrain_edges` 象限路径使用（相同的边界，相同的角规则，
   相同的重新计算法线），并且焊接网格被写回所有 1,156 个顶点。的
   注册的边缘是相同的，因此合并和象限单元相互焊接在一起。一个合并的
   焊接失败的单元并未失败：而是通过象限路径进行验证和焊接
   并计为后备，并注明原因 (`settle_cell_terrain`)。
4. `build_merged_mesh` 构建网格；一个修剪网格碰撞器是由相同的缓冲区构建的。
5. `NoData` 和 `Invalid` 单元使用象限路径，不变。每个单元格都有地形
   计算一次：`terrain_cells_merged`，或`terrain_cells_fallback`（带有
   `terrain_cells_fallback_expected_merged` 和 `terrain_cells_merged_invalid` 的细胞
   合并的数据符合预期或已损坏）。场景库存盘点拆分 `scene/terrain_patches`
   分为 `scene/terrain_merged_cells` 和 `scene/terrain_quadrant_patches`。

当阵列加载时，具有地形的外部单元的响应被保留（到达
顺序，一旦设置结束就首先重播），因此象限路径永远不会绘制单元格，只是因为
阵列迟到了。内部，没有 LAND 和失败负载的单元格不被保留，并且第一个
保留被记录一次。设置是有界的：如果没有设备判决到达（没有渲染世界的运行
立即发表拒绝声明；其他任何事情都会等待 `SETUP_TIMEOUT`) 或数组未完成
加载时，合并路径被拒绝，保留的单元格按象限绘制。暂缓回应
其负载已离开活动空间或卸载半径已过时：立即丢弃，
被视为陈旧的响应，并且其突出的插槽被释放。仍需要保留回应
保留其插槽，因此保留的积压保持在流式积压限制内。

块文件是内存映射的整体，并使用 `rkyv::access` 进行一次验证；地图开始于
页边界，这是 rkyv 需要的对齐方式，并且不会读取块的子切片。测试读取
由转换器自己的编写器生成的块。

不存在的块文件在剩余的运行中会被记住为丢失：转换后的文件
当引擎锁定资产时，资产就会被修复，因此丢失的文件将保持丢失状态，并且每个
没有合并数据的世界空间单元不需要进一步的磁盘访问。

＃＃ 网

位置、法线、UV 和 `COLOR_0` 等于今天的四象限网格顶点对顶点，
按象限顺序堆叠（4 x 289 个顶点、2,048 个三角形、`u32` 索引）。而不是包装好的
切线和第二个 UV 设置网格带有象限的槽：

|属性 |格式|地点 |
|---|---|---|
| `TerrainSlotIds0..1`（步幅为 16 时的 `..3`）| `Uint16x4`，插槽 0-3、4-7、... 的土地纹理 ID 8, 9 (10, 11) | 8, 9 (10, 11) |
| `TerrainSlotWeights0..1`（`..3` 步幅为 16）| `Unorm8x4`，插槽配重；槽 0 存储为 0 | 12, 13 (14, 15) | 12, 13 (14, 15) |

Ids 是表 id，从文件的 LTEX FormID 映射一次。着色器将槽 0 重构为
`max(0, 1 - sum of the others)` 并按 `terrain.wgsl` 的方式进行混合。步幅 16 是第二个顶点
布局，因此每次传递第二条管道。

## 材质和着色器

`MergedTerrainMaterial` 将最多 9 个漫反射和 9 个普通类数组绑定为静态
`texture_2d_array` 绑定（合约的最大值：三种块格式乘以每种大小的三种大小）
用法），一个采样器，id-to-（class，layer）表作为存储缓冲区和平铺常量。
`TerrainClassKey`，材质的绑定组数据，携带正在使用的类的数量，以及
`specialize` 将其转换为着色器定义，因此普通表编译的着色器只知道其
六堂课。采样的数组是数据，因此每个样本都是 `textureSampleGrad` 的导数
共享 UV 计算一次。

背面与今天的象限网格相匹配：它们带有切线，所以 Bevy 永远不会翻转它们的正常，
而没有切线的网格则在背面翻转。因此，着色器会报告每个
片段作为 Bevy 输入构建器的正面，地形由其插值法线照亮
从两侧。探测器在阳光下将一个单元颠倒过来，在 GPU 上进行检查。

group-4 绑定数组路径是后面的步骤。它的接缝是材料的结合处，两者
`sample_*` `terrain_merge/terrain_merged.wgsl` 中的帮助者。

## 限制

启动时，渲染世界将设备与表进行比较：类绑定加上
允许 Bevy 自己的纹理与 `max_sampled_textures_per_shader_stage` 相对应，每个阵列的
层数和表的 `max_layers_per_array` 与 `max_texture_array_layers`，以及每个
班级人数对照 `max_texture_dimension_2d`。任何多余的都会拒绝与数字合并的路径
在消息中。

## 数组检查

在加载任何内容之前，将读取每个数组文件的前 80 个字节以及该文件自己的
`vkFormat` 必须是使用的颜色空间中表的块格式（`_SRGB_BLOCK` 格式
对于漫反射，`_UNORM_BLOCK` 对于法线），具有列出的尺寸和层数。贝维的 KTX2
加载程序从加载设置中获取颜色空间，而不是从文件中获取，因此此标头是
只有放置错误的颜色空间文件才能被捕获。加载后，图像的描述符为
检查块系列、大小、层数、2D 阵列视图和重复采样器。数组是
作为仅渲染世界的资源加载，因此上传后像素的 CPU 副本会被删除；的
检查读取描述符，该描述符保留。

## 与象限路径的已知差异

- **权重按每个顶点插值。** 今天，着色器双线性插值 17 x 17
  每个片段的 VTXT 网格；合并的网格在每个三角形上插入每个顶点的权重。
  两者在网格点处一致，但在四边形内不同，因为三角形会插值
  重心性，而双线性面片则不然。哪一个符合Skyrim自己的插值是
  仍有待检查渲染比较。
- **绘制了更多层。**现在绘制了包含 7 至 16 层的象限；今天
  单元失败（`quadrant_layers` 拒绝超过 6 个）。转换器报告列出了这些单元格。
- **`TerrainCellMesh.key` 未被选中。** 引擎无法计算派生数据密钥（它需要
  插件记录），因此在 LAND 编辑或加载顺序更改后会绘制陈旧的块
  是的，只要它根据表进行验证即可。钥匙（`converter::terrain_chunks::cell_mesh_key`）
  是原始 LAND、LTEX 和 TXST 记录以及声明插件的主列表的哈希值。的
  引擎在加载时不保存任何这些（世界数据库和 `cell_cache.rkyv` 保存派生行），
  因此它无法重新计算密钥，并将存储的密钥与转换器也写入的密钥进行比较
  永远不会失败。 #185 的后续操作：重新转换会比较键并重写陈旧的块，因此
  陈旧的块永远不会到达引擎。
